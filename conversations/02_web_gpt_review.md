## 一、最重要的正确性风险

H3 官方明确区分逻辑父子关系与几何包含关系。细格的逻辑父格不一定完整覆盖细格，因此简单向上取父格可能与直接粗编码不一致。这属于 H3 已公开的基础性质，并非本项目的新发现。citeturn599116search8turn650925search7

目前的方法利用 `full` 模式筛选安全细格，思路具有条件正确性：

- 如果某细格确实完整处于其逻辑父格的几何区域内，而且点到 H3 单元的归属与这一几何判定严格一致，则该细格中的点可以直接采用逻辑父格。
- 其他细格重新调用 `latlng_to_cell(p, rc)`，可以保持与目标口径一致。

**关键问题在于：H3 4.5.0 的 `full` 返回结果不应无条件视为上述数学前提的证明。**

1. `full` 是 API 提供的几何筛选操作，不是经证明无误的全域安全证书。
2. 假阳性比假阴性危险：误排除安全细格只会增加重编码，而误接纳不安全细格可能导致错误聚合。
3. 现有杭州、南京实验尚不足以排除这种缺陷。

## 二、几何与数值局限

**几何近似与数值误差需要分开讨论。**

H3 的粗细网格来自不同分辨率的球面离散划分，并非严格嵌套。`cell_to_boundary` 返回的经纬度顶点、多边形包含判定以及 `latlng_to_cell` 的归属计算涉及不同的几何计算过程。H3 使用球面模型，而本项目使用 UTM 生成米制采样点。citeturn221282view3

UTM 采样本身没有问题，但存在三类局限：

**第一，边界表示误差。** 将 H3 边界转为多边形后，顶点舍入、边界插值和经纬度表示可能影响极近边界的包含判定。即使在杭州、南京通过常规验证，也不能外推至所有边界情形。

**第二，浮点归属歧义。** 理论上边界附近的一个极小位移就可能改变归属；在共享边或顶点处，数值实现的处理规则未必等同于普通 GIS 软件的 `contains` 或 `covers`。因此不能只用 Shapely 几何判定代替 H3 本身的参考输出。

**第三，覆盖范围局限。** 两座城市均属于常规中纬度场景，不能代表跨越 180° 经线、极区、五边形及二十面体面边界的情况。相关特殊几何行为在 H3 的问题跟踪记录中也有讨论。citeturn221282view1

应明确区分两个目标：

\[
\text{经验一致性：}\quad \forall p\in S,\ M(p)=D(p)
\]

\[
\text{全域一致性：}\quad \forall p\in\Omega,\ M(p)=D(p)
\]

其中 \(S\) 是实际测试点集合，\(\Omega\) 是目标适用域。当前证据支持前者在开发样本上的成立，不支持后者。

## 三、实验设计的潜在混淆

目前 90 组开发样本逐点一致，是有价值的正确性验证，但还有几个需要控制的实验变量。

**空间和随机种子的独立性不同。** 种子 100—109 与开发种子不同，可构成独立随机评测；但如果仍使用相同的杭州、南京区域和相同的 U/C/B 数据生成过程，就不能称为空间域外泛化。

**固定高斯簇可能有利于几何缓存。** 若不同批次持续使用同一组聚集中心，访问的细格可能高度重复。这是合理的重复工作负载，但必须报告缓存命中率，以及不同新批次实际出现了多少新细格，而不能仅报告加速比。

**B 分布的 ±20 米不等于数值极限测试。** 它可以制造粗格边界附近的归属压力，却不足以单独测试机器精度级的边界歧义。此外，9→8、10→8、10→9 的粗格尺度和细格数量不同，必须分别统计实际的边界跨越率、需要重编码的点比例以及内部细格覆盖率。

**逐点正确性与计数正确性应分别报告。** 计数向量可能在错误互相抵消时保持一致。既然开发集已经做了逐点验证，正式评测也应保留逐点核对，而不是只比较最终聚合计数。

## 四、计时基线与公平性

这是除正确性外最可能改变论文结论的部分。

如果输入是原始经纬度，直接粗编码只需一次 `latlng_to_cell(p, rc)`；所提方法却可能需要先细编码、建立分组、查询缓存、处理内部细格以及重编码部分点。

因此，即使方法减少了粗编码调用次数，也**不必然比直接粗编码更快**。

建议至少区分以下比较口径：

| 基线或方法 | 用途 |
|--------|--------|
| Direct-Coarse | 原始坐标直接粗编码，最重要的端到端基线 |
| Fine-Parent | 细编码后直接取逻辑父格，展示速度与错误代价 |
| Fine-Group-Recode | 已有细格分组，但仍逐点直接粗编码，隔离分组开销 |
| Full-Selective | 当前完整方法 |
| Cached-Cell-Lookup | 对细格缓存已验证的单一粗格归属或安全判定，评价缓存策略的实际贡献 |

这里的 Cached-Cell-Lookup 不能仅凭某个细格的中心点粗编码结果就认为整个细格安全，也不能把上一批次的点答案当成新批次答案。

计时必须明确分成冷启动、暖缓存和累计运行三个口径，并在相同输入状态下比较。如果细格编码是上游已经完成的，应再单独提供“已有细格索引”的增量成本比较，避免把上游成本不公平地计入某一方法。

建议使用以下成本分解：

\[
T_{\mathrm{total}}(K)
=
T_{\mathrm{init}}+
\sum_{b=1}^{K}
\left(
T_{\mathrm{group},b}
+
T_{\mathrm{lookup},b}
+
T_{\mathrm{recode},b}
+
T_{\mathrm{aggregate},b}
\right)
\]

需要记录 \(K\) 个不同新批次的累计时间，以及何时（如果存在）优于 Direct-Coarse。还应统一计时范围、硬件、线程设置、计数输出，并使用多次独立运行的中位数和离散度，避免将 Python 字典、内存分配或批次生成成本混入某一方案。

## 五、原创性主张边界

H3 的逻辑与几何非严格包含、`full` 筛选 API 和几何缓存均不能单独作为原创算法贡献。该 API 的实验性包含模式早在 h3-py 4.2.0 已经加入。citeturn599116search1

更合理的研究定位是：

**面向重复点计数工作负载，研究几何安全筛选、选择性重编码与缓存复用的正确性—性能权衡。**

可以将贡献限定在具体处理流程、可靠性边界、缓存摊销条件及不同空间分布下的成本分析。若实验不支持速度优势，仍可以形成有价值的负面结果与适用条件分析，但不应宣称提出了全新的 H3 层次结构、严格几何包含算法或普适高性能聚合方法。
